# Project review, 2026-10-23

Suggestions from a review of the whole project. The five top priorities were implemented straight after; the rest are kept here for later.
You asked for a review of the project: missing features, UX polish, code quality, edge cases and performance, ranked by impact with a rough effort for each. Two exclusions: no sign-in or user accounts, and nothing from the tmp folder.

Effort: **S** = under an hour, **M** = half a day to a day, **L** = several days.

## Top priorities (highest impact first)

1. **Keep free space on the datastore** (S–M). `capacity_blocker` ([api.py:363](backend/app/api.py#L363)) compares the template's full disk size with the free space right now. Three gaps:
   - **No space is held back.** A deploy can go through with only 6 GB left.
   - **Clones grow later.** Linked clones start small and fill up afterwards; a Wazuh server writes about 20 GB after it boots.
   - **Concurrent deploys aren't counted.** Several deploys close together can all pass the same check.

   This is the failure that paused VMs on 2026-10-23: when the datastore is full, every VM that writes is paused, the user's own included.

   Fix:
   - Add a `DATASTORE_RESERVE_GB` setting and refuse deploys that would go below it.
   - Let an extra declare `diskGB`, the same way it declares `minMemoryGB`, and count deploys that are still in progress.
   - Turn the Storage meter on the admin page amber, then red, as space runs low.

2. **Machines that depend on each other** (M). An agent stores its server's machine id ([extras.py:409-440](backend/app/extras.py#L409-L440)). Nothing warns you when that server is destroyed, reset or redeployed, or when DHCP gives it a new address. Each of these breaks the agent without any error showing. Wazuh's address has already changed once (from .65 to .7).

   Fix:
   - Add a "Used by" list on the server's page, and name the dependent machines in the confirm dialogs.
   - When `reconcile()` sees a server's address change, log a warning on each dependent machine.

3. **Cancel a stuck job** (M). A deploy can stay "busy" for the extras timeout plus each extra's `setupMinutes` (Wazuh's is over 15 minutes). While it's busy, `require_idle` blocks every other action, including destroy. Jobs waiting in the queue can't be removed either.

   Fix:
   - Cancel queued jobs (Procrastinate supports this).
   - Add "Stop waiting and mark failed" for a running deploy. The worker checks a flag in its wait loops ([actions.py:192](backend/app/actions.py#L192)).

4. **Expired machines count toward the quota** (S). The machine count in `deploy_machine` ([api.py:305](backend/app/api.py#L305)) includes expired machines, which wait out a 24-hour grace period before deletion. People get "Destroy one to deploy another" when nothing is actually running.

   Fix: either leave expired machines out of `max_machines`, or name them in the message with a "destroy now" link.

5. **Check capacity on the deploy form** (S). Running out of memory or disk is only reported after you press Deploy. The form already knows the machine's size, including memory and CPU added by extras.

   Fix: call `/capacity` (cached for 30 s) and show "Fits" or "Not enough memory: N GB free" next to the button.

## Missing features users would expect

- **User snapshots** (M). Reset only goes back to the "clean" state from first boot. Let people take one or two snapshots of their own and revert to them. Cap the number, because snapshots use datastore space (see item 1).
- **"Deploy another like this"** (S). Opens the deploy form with the same template, extras and options already filled in. Useful for agent fleets and for pairs of servers.
- **Deploy a server and its agents together** (M). Today it's two deploys, and the agent can only be started once the server is running. A combined option ("Wazuh server + N agents") would queue the agents to start after the server.
- **Expiry reminders without accounts** (M). The only warning is in the panel (`ExpiryWarning`). Add an optional webhook setting (ntfy, Teams, Slack, email relay) that posts "X expires in 2 h", using the owner's name.
- **Bulk actions on the machine list** (S–M). Stop, extend or destroy several machines at once, for example after a class or test session.
- **Download all sign-in details for a machine** (S). One file with the address, user, password and the extras' URLs, like the existing RDP download.

## UX and design polish

- **Hide "Soon" sections until they exist** (S). Pro Labs and Instances take two of the four sidebar entries and lead only to placeholder pages ([nav.ts](frontend/src/lib/nav.ts)). Planned services are mixed into the service list as greyed-out cards too. Put both behind a flag, or move them to one "Roadmap" page.
- **Show progress on long deploys** (S). Each extra already has `setupMinutes`. While deploying, show elapsed time against the expected time ("8 of about 15 min"), so a slow Wazuh install doesn't look hung.
- **Default to your own machines** (S). `myMachines` shows everyone's machines until you've typed a name once. After that, add a visible "Mine / Everyone" toggle instead of a hidden filter.
- **Fix the admin page's "Room for N more machines"** (S). It divides by the largest template's memory, but extras can raise a machine's memory above that. Base it on the largest real size (template plus extras), or show free GB only.
- **Show which templates are in use on the admin page** (S). A template can't be deleted while linked clones use it. Listing "used by N machines" per template makes clean-up safer. This was the same problem as with the datastore.

## Code quality: fragile, redundant or hard to maintain

- **Move extras' scripts out of `extras.yaml`** (M). The file is 1,591 lines, mostly bash inside YAML, so CI's shellcheck never sees it, and quoting mistakes only show up at deploy time. Put each script in `scripts/extras/<id>.sh` (and `.ps1`), have the YAML point to the file, and add them to the `scripts-check` CI job.
- **Split `prepare.sh` by extra** (M). It's 778 lines, with `bake_*`, `preseed_*` and per-distro filters for every extra in one file. Moving each extra into its own file, sourced by `prepare.sh`, would make adding an extra a single-directory change, matching the extras' scripts above.
- **Two catalogues of templates** (L). `frontend/src/lib/templates.ts` (363 lines) repeats `templates.yaml`, and a drift test guards it. Serve the display data (names, logos, descriptions, categories) from `templates.yaml` through `/api/config`, and the test is no longer needed.
- **The expiry sweep can loop while vCenter is down** (S). If an "expire" job fails, the machine goes to `error`. The next sweep turns it back to `expired` and queues another expire ([actions.py:357](backend/app/actions.py#L357)). The result is a warning in the log every minute, and the machine never reaches the destroy step. Fix: only re-expire when its last job wasn't a failed expire, or keep it `expired` when that job fails.
- **The capacity cache is held per process** (S, note only). `_capacity_cache` is a module-level global, which is fine with one uvicorn process. Add a comment, so that adding `--workers` later doesn't break the "deploys close together" check.

## Edge cases

- **Server address changes** (DHCP lease, reset, redeploy) break agents; see item 2. Also document DHCP reservations for long-lived servers.
- **Two people deploy at the same moment.** Both requests pass `capacity_blocker` before either machine is "deploying". This mostly matters near full; the reserve in item 1 also covers it.
- **The template is gone from vCenter but still listed in `templates.yaml`.** Deploys fail at the clone step with "Template not found". `/api/health` could check every listed template exists and has its "clean" snapshot, and the admin page could show this.
- **A long-lived machine's activity log grows without limit.** `prune_history` prunes jobs but not `log_lines`, and the machine page fetches the whole log every 3 s. See performance.
- **Names made unique by case** aren't a problem: names are lower-cased. The owner name is still taken on trust, which is out of scope here.

## Performance

No major concerns at this scale (10 machines, one panel server). Two small ones:

- **The machine page's log** (S): `GET /machines/{id}` returns the full log on every 3-second poll. Send only the last 200 lines (or lines after a given id), and prune `log_lines` for machines that have existed a long time.
- **Passwords in the list poll** (S): `/machines`, which every open tab polls every 3 s, includes every machine's password. Keep passwords only in `/machines/{id}`. This reduces what's exposed in transit and in browser memory. It isn't a sign-in feature.

## Suggested order if you approve everything

2. Item 2 (dependencies), then item 3 (cancel).
3. Moving the extras' scripts into files, and splitting `prepare.sh`.
4. User snapshots, "deploy another like this", combined server and agents, and bulk actions.
5. Last: the single catalogue (templates.ts from the API).
